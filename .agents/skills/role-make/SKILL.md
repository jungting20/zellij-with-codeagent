# Role Make

## Overview

Use this skill to add roles consistently in this repository. A role normally has three surfaces:

- Catalog metadata in `internal/roles/roles.go`
- CLI dispatch in `internal/cli/role/role.go`
- Role implementation under `cmd/agent-role/<package>/`

Follow the existing role style. Use `coding-agent` as the reference pattern for roles that launch an external command.
For roles with arguments, keep argument parsing inside the role package, not in `internal/cli/role/role.go`.

## Workflow

1. Clarify the role contract.
   - Role name, for example `coding-agent`
   - CLI usage, for example `coding-agent <path>`
   - Required and optional arguments
   - Whether the role only runs manually or should also be generated by planner flows
   - What command/process/UI the role should start

2. Inspect current role code before editing.
   - `internal/roles/roles.go`
   - `internal/cli/role/role.go`
   - Similar package under `cmd/agent-role/`
   - Existing tests in `internal/roles`, `internal/cli/role`, and the matching role package

3. Add tests first.
   - Update `internal/roles/roles_test.go` so the role catalog must include the new role.
   - Add focused tests for the new package under `cmd/agent-role/<package>/`.
   - Add or update `internal/cli/role/role_test.go` when dispatch behavior is observable without launching a real interactive process.

4. Add catalog metadata.
   - Add a `Role<Name>` constant to `internal/roles/roles.go`.
   - Add a `RoleSpec` with `Name`, `Usage`, `Description`, and `Arguments`.
   - Keep descriptions user-facing and short because they appear in `agent-role roles`.

5. Add the implementation package.
   - Create `cmd/agent-role/<package>/<package>.go`.
   - Expose `Run(args []string) int`.
   - Parse and validate role-specific arguments inside `Run(args []string) int`; return non-zero instead of calling `os.Exit`.
   - Put command construction or long-running role startup in small helper functions so tests can run without launching external interactive tools.
   - Wire `os.Stdin`, `os.Stdout`, and `os.Stderr` only in `Run`.
   - Return child process exit codes when launching external commands.

6. Wire CLI dispatch.
   - Import the new role package in `internal/cli/role/role.go`.
   - Add a `case roles.Role<Name>:` branch in `Run`.
   - Return the role package's exit code, for example `return network.Run(args[1:])`.
   - Do not add role-specific wrapper helpers in `internal/cli/role/role.go`; the dispatcher should only select the package.

7. Update planner code only when requested.
   - Planner-generated roles are usually in `internal/planner/page.go`.
   - Do not add a role to planner output just because it exists in the catalog.

8. Verify.
   - Run focused tests for changed packages.
   - Run `go test ./...`.
   - Run `go build -o bin/agent-role ./cmd/agent-role`.
   - Run `./bin/agent-role roles` and confirm the new role is listed.

## Naming

- CLI role names use lowercase hyphen-case: `coding-agent`, `network-tracker`.
- Go constants use `RolePascalName`: `RoleCodingAgent`.
- Package names cannot contain hyphens. Use a compact lowercase package name: `codingagent`, `network`, `console`.
- Commands in plans should call either `agent-role <role>` or the configured `zellij-agent role <role>` prefix, matching surrounding code.

## Error Handling

- Print concise validation errors to stderr.
- Return non-zero for invalid usage or failed setup.
- Avoid panics in role code.
- For external commands, preserve the child process exit code when possible.

## Testing Pattern

For roles that launch external commands, avoid requiring the real command in tests:

- Create a temporary fake executable.
- Set `PATH` with `t.Setenv`.
- Call the helper that prepares the command.
- Assert `cmd.Path`, `cmd.Dir`, and args.
- Do not run interactive tools in automated tests unless the role is explicitly non-interactive.
